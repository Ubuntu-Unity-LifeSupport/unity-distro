# Global menu in gtk-nocsd: the open gaps

Agent B, 2026-09-25/26, on `target2` (Unity session, our aptly packages; rolled
back to `Clean-2` afterwards). Follows `research/nocsd-reply2/`: each gap left
there is traced to its cause in the application's source or by measurement.
Where the fix is ours, it is built and measured; where it is not, there is an
estimate. Nothing was sent anywhere.

The patch is gtk-nocsd `main` (6b1f70a) plus the split parts of
`nocsd-reply2`, generated by `split/gen.py`. Two parts changed:

- **(a) cleaning and proxies**: it now also covers actions of groups
  inserted on a widget (item 1).
- **(d) deferred find and live menu** is new (items 2, 3 and 5). It is
  separate from (a), (b) and (c): `D`, `AD`, `BD` and `CD` build on their
  own. It is also where the base's menu search changes, and the maintainer
  said he would finish the base himself. So (d) is a measurement of what a
  later search catches, not a replacement for his work.

## 1. Dead items from `gtk_widget_insert_action_group` - fixed in (a)

**Cause.** GTK exports only the application's actions and the
`GtkApplicationWindow`'s own action map. A group an application inserts on
a widget with `gtk_widget_insert_action_group` is resolved by GTK's action
muxer, for that widget's subtree only. The muxer has no public API to list
it. This affected:

- Epiphany: `win.*` inserted on its window, which hides the window's own
  map.
- gnome-2048: `ui.*`.
- gnome-sudoku: `game-view.*` on the game view.
- Déjà Dup: `restore.*`.

The same holds for GTK3 and for the Unity panel's other GTK exporters:

- appmenu-gtk-module adds synthetic `unity.*` actions that activate the
  widget.
- KDE's and vala-panel-appmenu's importers only know `app.`, `win.` and
  `unity.`.
- No GTK issue asks for the muxer to be exported.

**Fix.**
- The library hooks `gtk_widget_insert_action_group` (an exported entry
  point, the same way gtk-nocsd hooks `gtk_window_present`). It keeps each
  group with its widget and prefix in its own list.
- For a menu item whose action is in such a group, the cleaned menu points
  at a stand-in in the window's map, `win.gtk-nocsd-<prefix>-<action>`.
  The stand-in:
  - takes the parameter type, enabled state and state from the group, and
    follows `action-enabled-changed` and `action-state-changed`;
  - activates through `gtk_widget_activate_action_variant` from the widget
    the group was inserted on, which is exactly how the muxer resolves it.
- Any widget of the same window is accepted, not only ancestors of the menu
  button. Sudoku's menu button is a sibling of the game view.
- When no group in the window has the action, the stand-in is taken out of
  the map, so items marked `hidden-when="action-missing"` stay hidden, as in
  the application. A later insert, replace or removal of the group rebinds
  the stand-ins of that window.
- `win.` actions are left alone unless the application inserted a `win`
  group itself (Epiphany). Celluloid adds its window actions after the
  window is realized, and without this rule they would have become
  stand-ins; a first build did that, and the audit caught it.

**Measured** (`results/groups-4.txt`, `results/groups-epi.txt`,
`tests/groupstest.c`, `tests/activate.sh`, `tests/sudoku.sh`):

| application | before | after |
|---|---|---|
| gnome-2048 | 2 dead | Scores and About work (the Scores window opens from the panel) |
| Epiphany | 6 dead | 5 `win.*` items work (Passwords opens from the panel); matches its own popover; "Uninstall web app" is missing, as in the application (hidden-when) |
| gnome-sudoku | 1 dead | "Reset puzzle" is absent on the start screen, disabled once a game starts, enabled after the first number, and resets the board |
| Déjà Dup | 1 dead | "Select all" is missing where the application has no restore view, as in its popover. `groupstest` covers the rest: insert, state follows, disable, removal hides the stand-in, reinsert binds again |

## 2. The GTK type bug and Gir.Core - no real application triggers it

Built with `dotnet-sdk-10.0` from resolute:

- `tests/GcMenu`: GirCore.Adw-1 0.8.1, an `Adw.Application` with a menu
  button.
- Pinta 3.1.2 (Gir.Core; it targets net8, so it runs with
  `DOTNET_ROLL_FORWARD=Major`).

Both load GTK through `NativeLibrary` (`dlopen`) and `DllImport` (`dlsym`).
On main 6b1f70a gtk-nocsd fetches the GTK types in both: the window type is
set once GTK is loaded (checked under gdb).

The bug of `nocsd-reply2` section 5 needs a GObject created *before* GTK is
loaded, as `typesorder.c` does. A Gir.Core application does not do that: it
initialises GTK first. The bug is real on main, but no real application
among these hits it.

GcMenu exports its menu (About, Quit).

Pinta exported nothing with (a)+(b)+(c): it creates its menu buttons after
`Present()`, so there is no menu to find at present or realize. With (d) it
gets its full menubar. See item 5.

## 3. gnome-contacts and gnome-tour

- **gnome-tour** has no menu button (its source has no `GtkMenuButton` and
  no menu model). There is nothing to export; not a gap.
- **gnome-contacts** on a fresh profile first shows its setup window
  (`did-initial-setup` false), which has no menu. With (d) the menubar is
  set empty for that window, and when the main window appears after setup
  its menu fills it (measured with ABCD). Once setup is done, later starts
  open the main window directly and export as the other applications do.

## 4. GTK3 applications with a header bar menu - estimate

Measured with `tests/probe3.c`, a GTK3 module that lists every
`GtkMenuButton` and what its menu is made of, on the 10 GTK3 applications of
`nocsd-reply2`:

| | count |
|---|---|
| main menu is a `GMenuModel` | 9 (Connections, Taquin, Tetravex, Four in a Row, Five or More, Hitori, Klotski, dconf-editor, Seahorse) |
| main menu is a hand-built `GtkPopover` (no model, cannot be exported) | 1 (gnome-disks) |
| of the 9: every item `app.`/`win.` | 6 |
| of the 9: items from inserted groups | 3: Taquin 2 of 3 (`base.*`), dconf-editor 6 of 6 (`headerbar.`, `bw.`, `ui.`, `base.`), Seahorse 2 of 6 (`pgp.*`) |
| window is a `GtkApplicationWindow` | 10 of 10 |

How much of the GTK4 code carries over to GTK3:

- **Menu search and export.** GTK3 has the same GMenuModel export
  (`gtk_application_set_menubar`, `_GTK_*` properties). Only the tree walk
  differs (`gtk_container_forall` instead of first-child and next-sibling).
- **Stand-ins.** GTK3 has no widget class actions, so only the group
  stand-ins of item 1 apply. GTK3 has `gtk_widget_insert_action_group` and,
  since 3.16, `gtk_widget_get_action_group`, so it needs no registry.
- **In-window menubar.** In GTK3 `show-menubar` defaults to TRUE, unlike
  GTK4. Where the shell does not set `gtk-shell-shows-menubar`, the exported
  menubar would appear in the window above the header bar. Part (c) is
  therefore required for GTK3, not optional.
- **Trigger.** gtk-nocsd already hooks GTK3 windows for its own job.

Estimate: about 150-250 lines on top of (a) and (c), with the same search
rules. It would cover 9 of 10 applications: 6 with `app.`/`win.` alone, the
other 3 through group stand-ins. Not built.

## 5. The menu is taken once - fixed in (d) where it is one window

**Cause.** The base takes the menu once, when the window is presented or
realized, and exports a copy. Anything the application does later is not
seen:

- Nautilus relabels Undo and Redo (`_Undo Rename`) by replacing the item.
- Pinta creates its menu buttons after presenting the window.
- Papers switches its stack from the start view (menu: Shortcuts, Help,
  About) to the document view (its own menus). Papers is also not a unique
  application: every `papers FILE` is a new process.

The "start" menu the base picked was wrong too. It exported the document
view's hidden sidebar menu, because at realize time no stack page is mapped
and both look visible.

**Fix, part (d):**
- **Empty menubar at once.** When a window is presented or realized
  without a menu, an empty menubar is set immediately, so GTK announces it
  on the window. The library then looks for the menu again every 250 ms,
  for up to 3 s, and fills the menubar in place.
- **Follow changes.** `items-changed` of the menu and of every section and
  submenu rebuilds the copy, coalesced into one idle rebuild.
- **Follow the shown menu.** An emission hook on `map` watches menu buttons
  in the source window; gtk-nocsd itself uses one for windows. When another
  button is shown, the search runs again and, if it finds another menu,
  switches to it.
- **Menubar-shaped menus.** A menu whose top-level items are all submenus
  (Pinta: File, Edit, …) is put on the panel as it is, instead of under the
  holder.
- **Second windows.** A second window of the same application only gets
  its stand-ins (the menubar is per application, window actions are per
  focused window).

**Measured:**

| case | before | with (d) |
|---|---|---|
| Nautilus, rename a file (`tests/naut.sh`, D-Bus `RenameURI`) | stays `_Undo` (ABC) | `_Undo Rename` (`_Отменить переименование`) |
| Pinta 3.1.2 | no menu (ABC) | its menubar as it is: File, Edit, … Layers, Add-ins, Window, Help |
| Papers start screen (`tests/papers2.sh`) | document view's sidebar menu (Open, Night mode, …) (ABC, and (d) before it followed shown buttons) | its own menu: Shortcuts, Help, About |
| Papers, `papers FILE`, sidebar collapsed | sidebar menu | the document menu: Print, Fullscreen, Presentation, `doc.*` items through the stand-ins of item 1 |
| Papers, document opened in the same window, sidebar shown | sidebar menu | switches from the start menu to the sidebar menu (primary) |

**Not covered:**
- A window whose two menus are both shown exports only one, by the same
  rule as at the start: shown, then primary, then most items. That is
  Papers' sidebar and document menus.
- Multi-window applications with different menus per window: the menubar
  belongs to the application.

Estimate for per-window menus: GTK exports one menubar per application,
but the `_GTK_MENUBAR_OBJECT_PATH` property is per window. It would need a
menubar exported per window on our own path, next to GTK's. Not built; no
application of the 44 needed it.

**The 44 applications with ABCD** (`results/var-ABCD3.txt`, against
`results/var-ABCD2.txt`, which is (d) without the `map` hook):

- Items that cannot be activated: 3. That is Epiphany's "Uninstall web
  app", Sudoku's "Reset puzzle" before a game and Déjà Dup's "Select all";
  all three are missing in the application too (item 1).
- Menus that changed:
  - Papers: the start menu, as above.
  - Console (kgx): every earlier variant, the base included, exported New
    Window, Fullscreen and Leave Fullscreen. That is a menu of a hidden
    page, not the main menu. Now it exports New Window, Show All Tabs,
    Fullscreen, Preferences, Keyboard Shortcuts and About; the theme and
    zoom widgets are dropped, as before.
  - gnome-contacts: exported this time only because its profile had done
    setup in the item 3 test.
- gnome-tour exports an empty menubar (the placeholder of (d), never
  filled). The panel shows no items, the same as without a menubar.
- Showtime timed out on its slow first start, as in every run; it exported
  its menu with a 20 s wait. Apostrophe opens no window.

## 6. Hiding the menu button, custom widgets - estimate

Unchanged from `nocsd-reply2`: 7 of 44 applications have items with a
custom widget (theme switchers, zoom, rotation, weather). These cannot be
exported. What others do:

- appmenu-gtk-module hides a GTK3 `GtkMenuBar` by overriding its class
  when `gtk-shell-shows-menubar` is set.
- KDE writes `gtk-shell-shows-menubar=1` and `gtk-modules` into GTK3's
  `settings.ini`.
- Nobody exports custom widgets: there is no format for them in
  `org.gtk.Menus` or dbusmenu.
- The only other GTK4 exporter found, fuhgawz-global-menu, is
  experimental.

Hiding the button would have to:

- apply only to the button whose menu is exported;
- come back when (c) withdraws the export;
- leave the 7 applications' widget items unreachable, unless a panel item
  opens the original popover, which needs the button visible to anchor it.

Estimate: small in code (a rough guess: tens of lines in (c)), but it loses items in 7 of
44 applications. That is May's and the maintainer's call. Not built.

## 7. Xfce and `environment.d` - known upstream, fixed in our package

**Cause, confirmed.**
- Debian's gtk-nocsd 4.8-1 sets `LD_PRELOAD` only through
  `usr/lib/environment.d/50-gtk-nocsd.conf`. Its maintscript removes the
  three Xsession scripts of the old gtk3-nocsd package
  (`01gtk3-nocsd`, `51gtk3-nocsd-detect`,
  `70gtk3-nocsd-propagate-LD_PRELOAD`).
- `environment.d` is read only by the systemd user manager. This is a
  known and open upstream request, systemd#7641; the Arch wiki says the
  same.
- An Xfce 4.20 session started by LightDM through Xsession is not a child of
  it (xfce4-session#213, systemd session support, is also open), so it never
  sees the variable.

**Other reports.** No report specific to gtk-nocsd on Xfce was found in the
Debian BTS, on Launchpad or on Codeberg. Codeberg's issue list could not be
fully checked. Upstream's README suggests `~/.bash_profile` or
`~/.config/environment.d`.

**Fix: `tests/51gtk-nocsd`, for `/etc/X11/Xsession.d`.**
- It adds `libgtk-nocsd.so.0` to `LD_PRELOAD` when the package is
  installed and the library is not there yet. That covers Unity, which
  already imports `environment.d`.
- It passes `LD_PRELOAD` into `STARTUP`, because `ssh-agent` (setgid
  `_ssh` on 26.04, started by `90x11-common_ssh-agent` in front of the
  session) makes the loader drop it. This is the same reason as the old
  `70…propagate` script.

**Measured on target2**, Xfce 4.20 through LightDM autologin, `tests/xs.sh`
reading `/proc/<pid>/environ` and `maps`:

| | xfce4-session, xfce4-panel, xfdesktop, xfwm4 | Unity: compiz, all 98 user processes |
|---|---|---|
| 4.8-1+unity1, no script | no `LD_PRELOAD`, library not loaded | `LD_PRELOAD=libgtk-nocsd.so.0` |
| script without the `STARTUP` part | `libgtk-nocsd.so.0`, loaded | - |
| script as packaged, `4.8-1+unity2` | `libgtk-nocsd.so.0`, loaded | once, no duplicates (0 of 98) |

On a default 26.04, `SSH_AUTH_SOCK` is already set by the user's
`ssh-agent.socket` or `gcr-ssh-agent.socket`, so `90x11-common_ssh-agent`
does not start an agent and the `STARTUP` part changes nothing. Where it
does start one, the part is needed. Measured directly:
`LD_PRELOAD=libgtk-nocsd.so.0 ssh-agent sh -c 'echo $LD_PRELOAD'` prints
nothing, and the same command with `env LD_PRELOAD=…` inside prints the
library.

The package is `gtk-nocsd 4.8-1+unity2` (`packages/gtk-nocsd`, branch
`unity/resolute`), built in a clean `sbuild -d resolute`. It installs the
script as a conffile of `libgtk-nocsd0`, next to `50-gtk-nocsd.conf`.

This is Debian packaging, not gtk-nocsd's code. Debian could carry the same
script (Debian's gtk-nocsd is packaged on salsa by the UBports team), but
nothing was filed.
